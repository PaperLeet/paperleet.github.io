# Community and interview filter continuity

Applied filter chips now share the same keyboard behavior across community discussions, per-problem solutions and the interview hub. Removing the focused chip moves focus to the next surviving chip, then the previous chip, then the existing search input. Clearing all filters returns focus to search. The read-only interview entry uses its stable notice when no search field is present. This focus handoff happens synchronously before the chip disappears; no timer or effect can steal later editor focus. Programmatic clicks leave a newer focused control alone.

Both chip groups use consistent 44px targets, borders, radii and theme colors. Long values stay on a bounded single line, with the complete escaped value retained in the accessible button name and native tooltip. Existing labels, filter order, query contracts, page reset, view/saved/solution context and locale-stable button identities are preserved. Motion respects the reduced-motion preference.

Chip and reset actions require a connected, visible, non-inert native button and the caller's current route/account lease. Retained hidden panels, stale routes and retired callbacks cannot focus or change the current view. Empty, failed and capability-gated views can still remove their active filters. No state, effect, dependency, API or schema is added to the filter action helper; it remains in deferred community/interview code.

Validation uses actual React StrictMode components and the existing full Community/ProblemSolutions/Interviews fixtures, including routing, query parameters, result cohorts, locale, stored private drafts and editor source/caret/scroll continuity. The standalone shared behavior fixture also covers next/previous/final removal, reset, escaped long labels, hidden/inert/stale/retired/detached controls and newer editor focus. Build checks retain initial-code budgets and deferred feature boundaries. These checks do not claim physical browser geometry or native pointer/IME behavior.
