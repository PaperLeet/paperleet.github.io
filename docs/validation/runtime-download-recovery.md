# Bounded build-time runtime downloads

A Pages build failed while downloading a pinned Pyodide package from jsDelivr: the connection timed out before the web build started. The build-time downloader now makes at most three attempts for transport/body failures, HTTP 408/429 and 5xx responses. Attempts keep the existing 60-second request deadline and use 1s/2s backoff. Retry-After seconds and dates are honored up to 30 seconds; a longer refusal ends the build instead of retrying early. Other HTTP refusals, digest mismatches and filesystem errors are terminal.

A valid SHA-256 cache entry is reused without network access. A successful response must match the unchanged digest from the pinned Pyodide lock before a temporary file is atomically renamed into the cache. Interrupted downloads cannot replace existing bytes, and temporary files are cleaned up. Package versions, lock digests, runtime contents and browser grading behavior are unchanged.

`node web/scripts/check-runtime-download.mjs` verifies valid cache reuse, connection/body recovery, permanent HTTP refusals, unchanged cache after bad integrity, numeric/date Retry-After, bounded long refusals, filesystem errors, real loopback HTTP recovery and real request timeout/exhaustion. Tests use disposable directories and close their server connections. This check is part of `npm run check`. The actual preparation command passes using the existing verified cache. A separate cold download of the pinned PyYAML 6.0.2 wheel from jsDelivr completed with the exact expected SHA-256 and was cleaned up.

The failed Pages job was independently rerun and the existing site recovered before publishing this script change. Production indexes, all six updated introductory details and a previous immutable detail were verified. Compact starters have identical decompressed bytes; gzip output may differ between export environments. The actual production course displayed all six new goals and restored 6/6 prior progress.
