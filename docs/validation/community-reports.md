# Open community participation and private reports

Active signed-in accounts can create/edit posts and replies without school/company verification. Affiliation remains optional verified display metadata, including anonymous posts; publication cannot fabricate a badge. Existing authentication, ownership, inactive-account checks, publication quotas and test-account mode restrictions remain. Current services advertise `community_open_publishing` and `community_reports`; explicit server denials remain authoritative and older deployments keep their legacy eligibility notice.

Cards and full discussions have a Report action. A native dialog loads only the current account's report state on explicit opening. Reasons include spam, harassment, privacy, misleading content, copyright and Other (which needs details). The reporter's identity/details are private; one account counts once per post, with 20 new reports per UTC day. Retry uses the captured command and request receipt. Closing/reopening can independently confirm a committed report; a later lost response cannot overwrite that confirmation. Input and newer editor focus survive asynchronous completion.

Administrators open **Community reports** in the avatar menu (`#/community/moderation`). The queue is ordered by pending distinct reporters, then cumulative reports, and supports minimum-count/status filters and pagination. Opening a case loads current content and five historical report snapshots per page. Reporter identities are omitted, and anonymous authors stay anonymous. Pending reports can be resolved by keeping the post or explicitly confirming deletion of the post and replies. A review note is mandatory; newer note drafts survive acknowledgement. Snapshots and review history persist after post deletion; deleting a reporter account anonymizes its report without destroying evidence.

New reporters reopen a kept case. Case revision and exact content-version checks prevent a stale review from closing newly arrived reports or deleting content edited after reading. Receipt replay confirms the original decision and cannot resolve newer reports. Report numbers do not cause automatic removal. The queue supports regular manual review; no scheduled review, external message or live moderation is performed during development.

## Validation

- `check-community-reports.mjs`: real React report dialog, card/full discussion, composer and administrator route. Personal-account posting, exact report/review retries, duplicate suppression, close/reopen confirmation, stale-content recovery, removal consent, retained newer notes/editor source/caret/focus, private role/loading/capability boundaries and bilingual behavior.
- The same UI flow can run against disposable native HTTP/SQLite through `PAPERLEET_REPORT_BRIDGE`, with real cookie sessions and server permission/receipt/version handling. Only a local mail fixture is used.
- Private moderation tests cover concurrency, per-account dedup/rate limits, privacy, inactive/guest/non-admin rejection, request binding, stale/new reports, content edits, retained evidence, author deletion, reporter anonymization, restart/foreign-key integrity and actual HTTP origin/current-account guards.
- Existing account/mail/OAuth/hosted tests now assert participation independently of badge proof while retaining authentication, profile privacy, tenant/identity, origin and private workspace isolation assertions. Full frontend/backend checks and three build profiles verify integration; report/review UI and styles stay deferred within existing initial bundle budgets.

These checks use source, React/JSDOM with a native-dialog polyfill and loopback HTTP/SQLite. They do not claim rendered browser layout, native focus trapping, device scrolling, real IME/clipboard, live OAuth/mail delivery or production deployment.
