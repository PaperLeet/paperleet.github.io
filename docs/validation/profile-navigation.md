# Profile activity and thread return context

Profiles use canonical `#/u/<username>?tab=<category>&page=<n>` links for Posts, Solutions, Replies, Likes, Reposts, Following and Followers. Default Posts/page one stay at the existing short URL. The parser accepts only a known lowercase username, one supported category and one bounded positive page; it rejects unknown/private fields, duplicate parameters, recursive returns and external destinations. Header account continuations and provider sign-in preserve this public context. No post body, comment draft or practice source is added to a URL.

App now parses the profile username separately from its query. Category/page changes update the controlled route while keeping the profile component and its identity/progress areas mounted. The hash handler retains the reader's viewport for changes within the same profile. Reloads, copied links, new tabs and browser Back therefore select the intended category/page. Sidebar shortcuts commit the corresponding first page before revealing its selected tab, and newer focus or scroll intent prevents a delayed reveal from taking over.

Profile post cards carry their canonical profile return context to full threads, including the separate full-page link on an inline solution reader. Detail navigation labels that destination **返回个人主页 / Back to profile**. Reply activity links additionally select the exact reply. Post/solution/reply/like/repost views reuse the existing owner-bound reading-return metadata and restoration notice; they wait for the matching activity response before restoring the actual source link, its viewport offset and keyboard focus. Reply rows bind both the post and reply ID, so several replies on the same post restore the actual selected source rather than the first matching post. Followers and following retain their own paginated URLs.

A response key prevents previous-category or previous-page rows from becoming current during a URL change. Pending, failed and timed-out activity reads keep the existing bounded recovery behavior. A last-page correction and an unsupported-Solutions fallback recheck the actual current profile URL before replacing it. A regression test reproduces a late empty-page response overwriting a newer destination before router cleanup; the final guard preserves that newer destination. An unresolved account capability waits before loading a copied Solutions context, and an older server falls back to the canonical Posts URL.

Anonymous rows in the author’s own profile use source-free public thread/reply links. Their profile return context stays in the existing account-bound session metadata; a shared link or fresh session exposes no profile association. The private return is unavailable to another account or a guest. Named/public profile navigation continues to carry its ordinary canonical URL context.

Private changes extend only OAuth return validation and its tests. Profile paths accept the same categories and page bounds; nested thread-to-profile returns are checked without accepting another nested destination. Existing community persistence, anonymous identity/count boundaries, quotas and account data are unchanged.

Verification covers mounted profile/thread traversal, delayed reading recovery and focus, stable profile identity across category navigation, browser Back, direct/reloaded links, reply targets, capability hydration/fallback, newer manual scroll and stale-route replacement. Existing profile, community navigation and reading-return regressions remain in the full suite. Provider tests exercise Google and Microsoft callback destinations and invalid context. Both editions, initial asset budgets and compiled styles are checked. This is React/JSDOM, local HTTP/session and source/build verification, not browser visual or manual OS UI QA.

Workflows remain manually disabled. No CI dispatch, release tag, online deployment or application production write is created.
