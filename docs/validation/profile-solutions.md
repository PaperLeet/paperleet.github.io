# Profile solution contributions

Personal profiles now offer a **题解 / Solutions** activity tab and a contribution count. The sidebar count opens the first solution page and reveals its selected tab; ordinary tab changes keep the reader in place. The server filters and paginates the complete author-scoped solution set before returning rows, rather than filtering a downloaded page of posts. The original Posts view still includes all posts.

Profile activity adds `tab=solutions`, an explicit `solutions:true` response acknowledgement, and `counts.solutions`. These use the same public activity boundary as Posts: visitors and other accounts see only named contributions; the author can also manage their anonymous solutions. Anonymous cards continue to display the anonymous identity and verified affiliation. Counts and rows follow the same visibility rule. Deleted posts disappear; edits do not reorder posts, and retired module context remains readable. Activity count, ordering and row reads share one SQLite snapshot. There is no new database schema or production data migration.

The UI requires a separate `community_profile_solutions` capability, so existing solution-feed support does not imply support for profile activity. It validates the acknowledgement and solution row type/module before rendering. Optional missing counts use an unknown marker instead of inventing zero. Own-profile solution views explain anonymous visibility and offer the canonical solution-feed entry when empty; visitors do not receive this private management prompt. Native disclosures provide the existing full Markdown/outline reader and per-card interactions.

Profile and activity requests now receive abort signals. Activity reads have a bounded twenty-second deadline with retry. Pagination is hidden while an activity read is pending or failed. A solution page beyond a newly shortened result set returns to its last valid page. Newer tab, account, capability or unmount state cannot be replaced by an earlier response, including late success after timeout. Existing profile tab keyboard controls now ignore composition and modified navigation keys. The content and social feature chunks remain deferred. The new profile-specific styles live in a dedicated stylesheet imported by the deferred community component, preserving the initial CSS boundary.

Mounted React/JSDOM checks cover capability rollout, deferred fetches, count shortcuts, paging/reset, full reading, keyboard/IME behavior, response confirmation, timeout/retry, stale tab/account/capability changes, guest and owner empty views, and both languages. Real loopback HTTP/session/SQLite checks cover author scoping, owner/visitor/admin anonymity, persistent counts, page ordering, edits/deletion, retired modules and response capability. Existing profile and community checks remain in the full frontend suite. No browser rendering or manual OS UI QA is claimed.

GitHub workflows stay manually disabled. This development wave creates no CI run, release tag, deployment or application production write.
