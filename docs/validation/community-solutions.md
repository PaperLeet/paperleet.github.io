# Problem and community solutions

The existing workspace `solution` tab is now labelled **题解 / Solutions**. It retains the explicit spoiler disclosure for the reference implementation and adds a deferred community solution feed for the current canonical module. Readers can expand Markdown, code and formulas, like, bookmark and read or write comments through the existing community cards. Search, sort, following/saved filters and pagination within this embedded feed stay local: they do not change the practice URL or replace the editor. Full thread links carry the canonical solution-feed return context.

The community sidebar has a Solutions view. Publishing there requires selecting a current practice module; publishing from a problem's solution area binds that module automatically. Only the entered title/body and explicitly selected publication fields are sent. Practice source and judge reports are not attached. A separate bilingual outline covers approach/derivation, implementation, complexity and edge cases. Empty outlines cannot be published. Existing anonymous publication preserves affiliation while hiding the public author identity.

The API adds an explicit boolean `solution` on posts and a boolean `solutions` feed filter. A solution must belong to a current canonical module and the implementation category. Its type and module cannot be changed after publication. Existing posts remain ordinary discussions. The private migration adds a default-false column and an index under the existing serialized schema-upgrade transaction; it does not rebuild tables or infer types from titles. Existing publication fingerprints, edit versions, reactions, replies, quotas and anonymous privacy behavior are retained. Solution publication receipts additionally bind the explicit type and module. Dedicated account/module solution draft scopes preserve ordinary drafts and captured retries.

The frontend requires the `community_solutions` capability and a filtered response acknowledgement. An older backend cannot silently show all discussions as solutions. Unsupported service, loading, empty, retry and expired-request states use the existing bounded feed lifecycle, and stale account/module responses cannot replace the current feed. A publication acknowledgement must confirm the expected solution/module before its receipt or draft is cleared.

Verification uses mounted React/JSDOM, real loopback HTTP/session/SQLite tests, existing frontend checks, both edition builds and emitted CSS/manifest inspection. DOM checks cover embedded URL/code/selection/scroll continuity, explicit publication, retry identity, selected-module drafts, outline insertion, capability and response guards. Backend checks cover persistence, filtering, social actions, anonymous affiliation, validation, immutable context, legacy migration and request replay. No browser rendering, hit-testing or manual OS UI verification is claimed.

Production publication remains held. GitHub workflows remain manually disabled, with no CI dispatch or deployment in this development wave.

Topic discussion and solution lists now cross-link within the same canonical module. A solution list returns to all community solutions and labels its default filter as all solutions. Source-free solution threads label their existing return target as the module solution list. Retired modules retain historical reading links without offering a practice action. These links use the existing native anchor navigation and do not publish content or convert ordinary drafts. The mounted solution check covers scoped switching, filtering, retired-module links, draft retention and absence of extra mutations.
