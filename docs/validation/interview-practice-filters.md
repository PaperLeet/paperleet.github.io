# Difficulty and per-exercise duration in interview preparation

The frequent-concept view offers native difficulty and per-exercise duration selectors. They filter both report-backed concepts and the curated fallback list, before learning-state counts, progressive display and batch candidates. Difficulty supports Easy/Medium/Hard; duration supports at most 15/30/45/60 minutes. This is a limit on each exercise, separate from the batch planner's total time budget. Preparation paths below remain complete.

Filters retain the existing source/curriculum order and original community ranks. They neither request different source statistics nor infer company frequency. Missing required metadata is explicitly counted and excluded from a constrained result; no missing estimate counts as zero. Search-empty, metadata-filter-empty, unavailable-catalog and unresolved progress states remain distinct and recoverable. An explicitly captured batch keeps its public-number snapshot even if one exercise is outside the current list filters.

Bounded `difficulty` and `max_minutes` parameters belong only to `view=questions`. Canonical links, active chips, individual/combined clear, sign-in returns, exact practice queues and public checklist sharing retain them. Links to reports/companies discard them. Source previews keep the complete original reading return while their report requests remain free of practice-only parameters. Changing metadata criteria starts a new local selection scope; starting practice captures its exact ordered batch as before.

Controls remain in the stable hub toolbar across list remounts, retaining native keyboard focus and localized labels. Workspaces, accepted grades, source contributor counts and unpublished drafts are not changed or serialized. Defaults preserve existing routes and behavior. The new result UI remains deferred; initial build limits and the three-asset graph remain required.

`check-interview-practice-filters.mjs` covers four registered controlled React/JSDOM and pure-model groups, plus an optional actual public summary HTTP/SQLite flow via `PAPERLEET_PRACTICE_CRITERIA_HTTP`. Backend checks cover strict and nested navigation grammar and actual signed Google/Microsoft callback continuation with vendor responses stubbed. These checks do not claim browser rendering, physical IME/native focus trapping, OS clipboard or live-provider validation.
