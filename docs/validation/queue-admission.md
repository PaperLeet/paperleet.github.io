# Bounded server queue admission

The user story is browser/CPU feedback → optional server confirmation → waiting for an available queue slot → one authoritative run → source-bound results without overwriting newer edits. The existing durable FIFO already waits when a worker explicitly refuses before execution. This change covers capacity rejection before a job has joined that queue.

## Admission and recovery rules

Only HTTP **429** with the explicit **`queue_full`** code permits an automatic retry. All attempts retain the same request ID, captured source, module, local client ID and expected account. Retries honor numeric/date Retry-After values, occur at least **10 seconds** apart, and stop starting new requests after a **120-second monotonic deadline**. This stays below the existing per-account ten-submissions-per-minute limit. A Retry-After longer than the remaining budget ends the wait rather than retrying early. An acknowledgement already in flight is still resolved; the deadline does not prove that such a request was refused.

Generic rate limiting, authentication/access conflicts and other refusals are terminal. Lost, 5xx or malformed success acknowledgements switch to GET-only tracking of the same ID. The account and client bindings remain enforced by the existing server. No queue capacity, native isolation flag, account-acceptance rule or numerical/browser suite changes.

The waiting notice distinguishes **not yet admitted**, **confirming admission**, **queued**, and **running**. The source snapshot is held in memory, can be reviewed/downloaded and is never replaced by later edits. Review stays open through another admission attempt. During an in-flight request, Stop waiting is temporarily unavailable; a stale stop event cannot discard an uncertain receipt. Once a full-queue response has arrived, stopping aborts the delay without creating a job. Logout, owner changes and unmount abort old work and suppress late callbacks.

Only an ID/module receipt is stored in tab session storage. An explicit queue_full refusal removes it; refresh stops slot waiting and cannot resume automatic POSTs or execute stored code. Admitted or uncertain receipts reconnect through GET. The user-facing notice explains this distinction. Missing storage can reduce receipt recovery, but cannot authorize an automatic source replay.

The extended countdown/review component and server controller load on demand. Their fallback retains the captured-code download and stop controls if the notice chunk fails. The controller and admission policy are removed entirely from browser-only Pages builds; the build check enforces this and deferred loading in editions with a native server. The original 400 KiB raw / 130 KiB gzip initial-JavaScript caps remain unchanged.

## Evidence

- `check-queue-admission.mjs`: immutable source/ID/account despite mutable caller inputs; explicit-refusal classification; Retry-After seconds/date; two-minute expiry with a backward wall-clock jump; long Retry-After; stop/account abort; lost/malformed acknowledgements; JSON errors; bilingual notice and fallback controls; no hidden source dump while review is closed.
- `check-queued-controller.mjs`: duplicate clicks, stopped delays, in-flight cancellation races, review continuity during retry, existing-receipt restoration without source replay, lost/malformed acknowledgements, cancellation of an admitted queued task and immediate owner isolation. The same deferred controller is used by the React hook.
- Shared native FIFO/catalog checks: **31 passed**. The real hosted HTTP boundary additionally proves queue_full returns 429 / Retry-After 5 before creating the target job, then accepts the identical request ID and saves exactly one run after capacity is freed.
- A disposable loopback hosted edition uses real test-account sessions, private workspace synchronization, SQLite queue admission and native execution restricted to exact reviewed Attention fixtures. Synthetic load occupies the single test queue slot; it is not represented as a graded implementation.
- While the first submission waits, a later editor change remains saved. The downloaded captured source exactly matches the original. Freeing capacity produces one native execution of that original SHA-256, **7/7** tests and one account run; the newer draft remains intact and the UI labels the result as older code.
- A deliberately malformed 202 acknowledgement followed by refresh produces **one POST** and subsequent GETs of its admitted ID, returning a second **7/7** result without another execution. Native executions total two for these two authorized fixtures.
- Stop waiting restores Ready. Refresh of a not-yet-admitted wait does not replay source. An already successful browser run followed by server waiting shows the active server state instead of the old browser stage. Logout during waiting clears the old controller; a second account shows its own starter and no old captured code, result or waiting controls.
- An intentional optional-notice 404 on a separate loopback origin retains working Stop/download controls at **390 × 844**; body/viewport widths both measure **390 px**. A normal proxy tab downloads the fallback snapshot byte-for-byte; mobile Stop works. The iframe download-event retrieval timed out in automation, so that retrieval is not represented as verified. The failed chunk cannot prevent stopping. A separate transient editor fetch failure recovered after refresh, with code and both server results preserved; it is not counted as a successful rich-editor load before recovery.

The complete frontend check chain and TypeScript/production builds pass.
